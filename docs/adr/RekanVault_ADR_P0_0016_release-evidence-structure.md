### RV-DEC-0016 — Release evidence folder structure and naming

- Phase: P0
- Status: Approved
- Owner: Sigit
- Date: 2026-07-31
- Decision required by: Before P1-GATE closes (first phase gate requiring retained evidence)
- Context: SDLC plan section 2.2 requires every phase to produce "measured evidence that the exit gate passed," and section 19 lists specific artifacts every release candidate must retain (git commit, migration revision, contract versions, model IDs, golden-set revision and metrics, security scan reports, resource profile, backup/restore proof, known limitations, go/no-go record). Neither document defined where this evidence physically lives or how it's named — to-do item #8 flagged this as an open gap.
- Options:
  1. No defined structure — evidence accumulates ad hoc (screenshots, scattered files, chat logs).
  2. One dedicated folder area, `docs/release-evidence/`, structured as one sub-folder per phase (P1–P10) and, for P11 specifically, one sub-folder per versioned release candidate (matching the alpha/beta/rc/final progression already defined in SDLC section 2.4).
- Chosen option: Option 2.
- Why: Without a defined location, gate-passing evidence tends to scatter and becomes unverifiable later — exactly the kind of untraceable state this project has been actively avoiding (see the ADR system itself, and RV-DEC-0015's golden-set discipline). Structuring by phase keeps evidence directly traceable to the specific gate it proves, mirroring the phase structure already used throughout the SDLC plan. P11 needs finer-grained sub-folders because, unlike P1–P10 (one gate each), P11 produces multiple release candidates before the final `0.1.0` tag.
- Impact:
  - New top-level structure: `docs/release-evidence/P1/`, `P2/`, ... `P10/`, and `P11/0.1.0-alpha.1/`, `P11/0.1.0-beta.1/`, `P11/0.1.0-rc.1/`, `P11/0.1.0/`.
  - Each phase folder should contain, at minimum: a gate-summary document (pass/fail against that phase's exit-gate criteria, date, sign-off), and whatever specific artifacts that phase's test plan produces (e.g. P4's golden-set results, P10's security scan reports).
  - This folder sits alongside `docs/adr/` (decisions) and `docs/plans/` (workflows/process docs) as a third top-level `docs/` area — evidence is proof, not decision or process, and is kept structurally distinct.
  - Lives alongside the ADR system (Drive-managed for point-in-time content), but since evidence files (test results, logs) are typically generated by tooling/CI rather than hand-edited, this folder is expected to eventually be populated by the coding agents' pipelines directly, not manually curated like the ADRs.
- Reversal trigger: If phase-based structure proves awkward once CI/automated evidence generation exists (e.g. tooling expects a different convention), revisit naming — but the core principle (one traceable location, structured by phase/release-candidate) should hold regardless of exact folder mechanics.
- Related ADR/tests: SDLC plan section 19 (Test Pyramid and Release Evidence), section 2.4 (release candidate progression), P1-GATE onward (every phase gate from here forward should populate its corresponding folder).
